## Worktree launcher (sequence step 2 of `2026-10-07-a-session-can-run-in-its-own-worktree.md`)

Operator: "work on adding the automatic worktree creation and directory creation to the
launcher given that: The user points the CWD (project root) to a genuine repo and a feature
branch name is populated."

- **W1 — Base (answers that record's O1) (D).** The `HEAD` of the cwd checkout. No fetch ever,
  no base field. A warning when that checkout has uncommitted changes, because they are not
  carried into the new tree.
- **W2 — Branch name (D).** Exactly as typed. No `pptmstr/` prefix; the record's R-proposal for
  one is not taken. Cleanup (step 5) will have to find pptmstr's worktrees by placement under
  `~/.pptmstr/worktrees/<repo>/` instead.
- **W3 — Existing branch (D).** If the D4 path is already a registered worktree on that branch,
  the launch reuses it. Any other collision is refused with the draft kept.

  **Revised by the lead on board task wt-fix-2 (unattended session, not ratified by the
  operator): no existing worktree is reused, in any state.** If the placed path or the branch
  already has a worktree, the launch is held with the draft kept and one line naming it: "to
  continue there, set the directory to <path> and leave the branch empty", which is today's
  launch in an existing directory. The reason: git does not record whether an add finished. An
  add stopped at its limit inside `post-checkout` leaves the tree registered, unlocked and on
  the branch while the hook is still writing into it. Run on 2.39.5, the old reuse path
  started a session there. An add killed and then unlocked by the operator looks the same. So
  no reading of the listing makes reuse safe. W1's uncommitted-changes warning moves to after
  the press as well, for a different reason that the 2026-10-07 record's "Step 2 follow-ups"
  measures: a dirty press is held once, and pressing again launches. Refined on wt-fix-3 and
  wt-fix-4: the "continue there" line is offered only for a path git lists as a worktree,
  unlocked, and with no unfinished add recorded for it by this process. It says the tree may
  be incomplete, and it never advises running a command inside the tree, because a session
  can aim a tree's `.git` at a repository it built.
- **W4 — "Directory creation" (D).** The missing parents of `~/.pptmstr/worktrees/<repo>/`. The
  cwd is never created.
- **W5 — A failed creation (answers O4) (D).** Holds the launch through the existing
  `report_failure` path: no session, git's or the pre-flight's reason shown, draft kept. Never a
  silent fall back to `STRICT`.
- **W6 — Out of scope (D).** D2's "AUTONOMOUS requires a linked worktree", the missing-paths
  notice (step 3), the ref sensor (step 4), removal (step 5). An empty branch field is today's
  behaviour, byte for byte.
- **W7 — Launching from a linked worktree (D).** Allowed: based on that worktree's `HEAD`,
  placed under the main repository's name. `worktree.py`'s docstring says `main_root` is a claim
  the directory makes; the operator chose that directory, which is the ground for accepting it.

## UI

- **U1 — Tool calls and results are structured transcript entries (D).** Name, inputs, full
  output, error flag; each output capped at 1 MB. The present text line is derived from the
  entry, so the panes draw what they draw today until the terminal-style rendering lands. Today
  `driver.py` cuts each argument to 60 characters and a result to 300 when it writes the line,
  and keeps nothing else, so neither an expand/viewer nor the reworked tool line has anything
  to draw from.
- **U2 — Typeset is the only mode chosen (D).** WRAP stays as the fallback where the library is
  absent (Linux aarch64). RAW and RICH are to be deleted. **Lead's narrowing for this round:**
  the mode choice leaves the UI and the default becomes TYPESET, but the RAW/RICH code is not
  deleted until the operator has reviewed the rest — a deletion is the one change here that is
  expensive to review after the fact.
- **U3 — Scrollback (D).** About 10k lines held in the pane; older output through the viewer.
  **Measured and refused at 10k (builder-5, `pane-geometry`, run on `bench_panes`' synthetic
  turns, one machine):** the deciding cost is not the first frame but a width change, which lays
  every held generation out again — 20 ms at 1k lines held, 30 ms at 1.5k, 198 ms at 10k (about
  5 fps while a splitter is dragged). The typeset pane holds 1,500 lines (`_TYPESET_KEEP`) and
  takes in 400 when a session is first shown (`_TYPESET_WINDOW`): `pane-geometry` raised the
  window to 1,000 and `pane-fix` put it back, because the first frame on a long session went
  from 53-61 ms to 117-140 ms (builder-9, run; the table is in the docstrings). Everything older is
  reachable through the pane's "earlier lines" control, which shows the RAW renderer until the
  viewer exists. What would lift the limit: not re-laying out generations that are out of sight
  when the width changes.
- **U4 — The always-shown scrollbar (D).** `_draw_typeset` forces it so the text width never
  changes under a re-layout. Keep the gutter reserved, draw the bar only on overflow. Separately,
  measure the height: the fixed 150 px held for the composer (`app.py` `session_pane`) is a
  candidate for the overflow the operator sees, unconfirmed.
- **U5 — Syntax highlighting and backgrounds (D).** Pygments becomes a direct requirement
  (imscribe ships no tokeniser; the host brings one). Code and terminal-block backgrounds are
  drawn by pptmstr from block geometry, since imscribe's theme excludes per-block fills. What
  imscribe should grow is written as issue drafts under `planning/`, not filed.
- **U6 — Menus (D).** Native OS menus are deferred to a research note (hello_imgui has none;
  macOS would mean pyobjc and Linux has no common global menu). In ImGui: the focused card's
  actions directly in the Session menu instead of "Controls for the focused card…", short
  labels, chord hints read from the bindings that act on them, and our own replacement for
  hello_imgui's View menu ("Select layout").
- **U7 — Fleet pane: no change.** Operator: "Looks like accurate current state." The lead notes
  the pane is a 21 % dock split with no width bounds; it looks fixed because the ini restores
  the splitter.
- **U8 — Board header (D, operator: "Yes, that's fine.").** Routine provenance lines ("restored
  from a log…", "recorded in …") move to the session details modal; any `Tone.ALARM` line (a
  short or refused restore, records not kept) stays above the scroll, for the reason
  `board_pane._log_lines` gives. The board gains a state filter (open, held, waiting, done).
- **U9 — Pane tabs (D).** Lowercase labels with the present names kept as `###` ids so saved
  layouts survive; the inset rounded tab shape is prototyped before it is adopted.
- **U10 — Look and feel is picked, not chosen for the operator (D).** A probe renders 2-3
  variants of the shared style decisions — spacing, rounding, scrollbars, tabs, buttons,
  margins, the monospace output block — on the same screens, and nothing is applied to
  `theme.py` until the operator picks.

## DETAIL acts in FOCUS only (2026-10-16)

The operator: "parked concerns that are actionable (approvals, break-glass, questions) should
be actionable from the detail pane. That allows operator functions without leaving focus
mode." And then: "That _only_ makes sense if the user is in Focus-Mode. Triage would read odd
with double interactive functions in both the inbox and detail."

This amends the 08-11 rule ("the inbox row is where you act, DETAIL is what informs the act",
cited in `2026-08-13-detail-swaps-to-a-deliverable.md`) and does not discard it. The rule held
because NEEDS YOU was on screen. The FOCUS layout has no NEEDS YOU pane, so there approvals
answer only to keys, `e`'s editor has nowhere to draw, and break-glass commands and decisions
cannot be acted on at all. The new rule: **in each layout there is exactly one place to act.**
In TRIAGE that is the inbox row. In FOCUS it is DETAIL, using the inbox row's own controls (the
same code, not a copy). Questions already act through SESSION's composer in FOCUS. Still to
settle with the operator: which kinds (approvals, break-glass commands, decisions), and whether
the approval editor draws in DETAIL.

  history-to-digest) So DETAIL shows only what is in front of the operator.

## The operator's notes, verbatim

```markdown
# UI overhaul

This is a general notes and ideas document that I've developed during the dogfooding phase
of using pptmstr with imscribe and enhanced.

## Aesthetic wins

Now that we have a pretty strong typesetting library that is also performative I think we ought to consider the aesthetics of lot of our output and work towards a design consistency. Here are some low hanging fruit.

### Session Pane

The SESSION pane is now incredibly important. With markdown and selectability we've gained some wins but a large part of output are bash commands and output of tools.  These can be cleaned up by using type and formatting and dropping intro text like `Bash ->` A new style of output could be something that evokes terminal output (monospace gray font on pure black or nearly black background).  If the output is to be truncated then a expand tab that will open an output viewer (potentially a separate top-level view window) tab. 

Also the tool line (blue with "Bash(command=..." could be reworked in order to display more of the bash command (monotype) with the description, timeouts, etc in smaller type variable-width abover the command.  Edit, WebFetch and others could also have developed "intro" blocks that communicate what the agent is doing/has done and a truncated output.

Scrollback should be extended.

The current pane is being rendered where the height is overflowing and always presenting a scrollbar. This needs to be fixed.

Session pane preferences get moved to a settings dialog.
Defaults:
- Reasoning: On
- Typeset selected (potentially depracate raw,wrap and rich)
- Follow is inferred by scrollbar locking
- Remove filter (supplanted by a new find)
- Find function overlay (using imscribe features)

Add _about_ one endash of margin on left and right.

If supported, when markdown defines a language for a codeblock we should allow sysntax highlighting. This _should_ be supported by imtypeset and imscribe. If not then we need to make issues for them.

## Menus

Find a way to plug into the host OS's menu system and regain some control on ordering.

"Controls for the focused card" should be replaced with the menu items _directly_ that would control the focused card.  Not just a shortcode to open the context window.

Menu item text should be _short_ first and then descriptive while also showing any global key-chords that invoke the function.  Session menu items do, Select layout does not hint.  _No wordy help text_.

## Fleet Pane

This is an interesting one but the fleet pane is now _fixed_ and the width is capped.  It would be the constant of the applications UI right now.

## Settings Dialog

The settings dialog starts collecting all settings and organizes them by a left side navigation pane.  Appearance, Text, Panes, Theme, etc.  This will allow future growth of more technical settings as well.

## The Board

Seeing the tasks that are pending vs claimed would be useful for quick overviews especially whenn the history gets long.  Filtering will go a long way.

The header is also geting too wordy. "Restoration" and "recorded in" belong to Details dialog.


# Cohesion and UI workshopping

We may want to workshop and UI style/theme around these using well defined UX/UI guidance but also keepin a hacker/developer aesthetic which may run counter some of the modern trends of UI (oversized margins, hidden affordances, etc)

## Scrollbars

Prefer slightly larger scrollbar with rounded ends.

## Tabs for Panes 

Tabs for panes are rendered larger (~10-15%) with rounded four corners inset into the tab "lane"(newer Firefox style or VS Code. Text is rendered all lowercase rather than uppercase.  Bottom margin on text is balanced with the margin top.

## Buttons

Many buttons don't read as buttons and have too tight of margins.  Removing the outline and choosing a flat render with rounder corners may be enough to differentiate them from input/text wells.
```
